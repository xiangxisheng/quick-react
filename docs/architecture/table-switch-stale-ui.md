# 数据管理切换表格时 UI 混合问题复盘

## 现象

在数据管理页面中，先打开一张表，再切换到另一张表，页面可能出现以下现象：

- 新表的列和旧表的列混在一起；
- 新表的数据行中出现旧表记录；
- 旧表的操作按钮或查询条件仍然存在；
- 快速连续切换时，最后选择的表格被较早返回的请求覆盖。

这类问题看起来像“React 没有清空 UI”，但实际是页面复用了同一个表格组件实例，同时多个异步请求和多组状态更新交错执行。

## 根因

数据管理的表格页面路径始终是同一个，例如 `/panel/admin/data/rows`。切换数据表时，只改变 `table` 查询参数，并不会改变 React 路由路径。因此 React 会按照正常的协调（reconciliation）规则继续复用 `TableCRUD` 组件。

组件复用本身是正确行为，问题在于旧实现没有把“表名”视为表格实例的身份：

1. 旧表的 `dataSource`、`columns`、操作配置和查询状态保存在组件 state 中；
2. 切换表格后，新请求尚未返回，旧 state 仍然可以继续渲染；
3. 如果旧请求比新请求晚返回，它可能把旧数据再次写回 state；
4. 如果响应没有完整返回某个配置字段，旧实现会保留原来的字段，造成配置残留；
5. Ant Design Table 还可能保留当前实例内部的列、选择和分页状态。

因此这是应用状态管理和异步请求生命周期的问题，不是 React 的 bug，也不是 React 的普遍缺陷。React 只是在按照组件类型和位置复用实例；如果业务上要求“换表就是一个全新的表格实例”，应用必须明确表达这一点。

## 为什么普通 UI 设计通常会考虑到

成熟的列表组件一般都会同时处理三件事：

- 使用资源标识（这里是表名）作为组件 key；
- 切换资源时清空旧数据和旧配置；
- 只接受当前请求的响应，丢弃过期请求结果。

如果只做其中一项，仍可能出现短暂残留或竞态覆盖。尤其是“同一路径、不同查询参数”的页面，不能只依赖路由卸载来清理状态。

## 本项目的处理原则

当前实现采用四层保护：

### 1. 用资源身份重建表格实例

`Table` 使用当前 `table` 查询值作为 key，表名变化时强制卸载旧的 Ant Design Table 实例并创建新的实例。

外层页面也使用后端页面路径作为 `TableCRUD` 的 key，避免不同后端页面复用同一列表实例。

### 2. 切换时立即清理旧内容

点击查询/切换表格时，先清空：

- 数据行；
- 列定义；
- 列缓存；
- 分页和选中行；
- 当前请求游标。

查询控件本身保留，方便用户继续选择新表；表格内容在新响应返回前保持空白或加载状态。

### 3. 后端响应完整替换配置

每次收到表格响应，都完整替换 `option`、查询字段、列定义和数据源。响应中没有字段时显式清空，而不是沿用上一张表的 state。

### 4. 丢弃过期请求

组件为每次请求分配递增序号。切换表格后，旧请求即使晚返回，也不能覆盖当前表格的 state。

## 为什么不能只调用 `setDataSource([])`

只清空数据行并不能解决问题，因为列定义、操作按钮、查询字段、分页、选中状态和 Table 内部状态仍可能属于旧表。反过来，只替换列定义也不能解决异步竞态：旧请求仍可能把旧数据写回。

因此必须把“资源切换”当成一次状态边界，而不是普通字段更新。

## 结论

这次问题的性质是：

- 不是 React bug；
- 不是 React 必然存在的通病；
- 是应用没有明确建模“表名对应独立表格实例”，并且没有处理异步请求竞态；
- Ant Design Table 的可复用内部状态放大了问题的可见性，但不是根本原因。

以后所有后端驱动的列表、表单和数据源切换，都应遵循同一原则：资源标识变化时清理旧状态、必要时更换组件 key，并拒绝过期响应。前端不推断业务流程，但必须正确维护通用组件的生命周期和请求隔离。

## 2. 后端驱动按钮

### 2.1 目标与最小数据原则

列表、表单和页面操作按钮由后端输出，后端决定：

- 是否显示；
- 显示文案；
- 按钮顺序；
- 是否禁用；
- 是否需要确认；
- 动作类型；
- 动作参数。

前端不再硬编码具体业务按钮名称、业务按钮权限或业务按钮顺序。

后端输出遵循最小数据原则：只输出前端无法根据已有上下文推导出的信息。默认行为不需要显式描述：

- 能通过 `key`、当前页面资源和后缀生成的 URL，不返回 `url` 或 `href`；
- 正常显示的按钮不返回 `visible: true`；
- 默认可用的按钮不返回 `disabled: false`；
- 能由标准 `action` 推导的请求路径、资源 ID 和刷新行为，不重复返回；
- 页面和 API 的公共前缀、路径后缀不放进每个按钮配置。

只有改变默认行为时才返回对应字段，例如 `visible: false`、`disabled: true`、确认配置或自定义参数。

### 2.2 标准 CRUD 动作

标准 CRUD 动作不由后端重复提供路径。前端根据当前页面的 `resourcePath`、行主键和动作类型生成 API 路径：

```text
create -> POST   /api/<resourcePath><apiSuffix>
edit   -> PUT    /api/<resourcePath>/<id><apiSuffix>
delete -> DELETE /api/<resourcePath>/<id><apiSuffix>
refresh -> 重新加载当前资源
```

后端只需提供类似以下语义配置：

```ts
{
  key: 'delete',
  label: '删除',
  action: 'delete',
  method: 'DELETE',
  confirm: '确认删除吗？'
}
```

`action` 和 `method` 是两个不同概念：

- `action` 表示前端要执行的业务交互动作，例如 `create`、`edit`、`delete`、`refresh`、`navigate` 或已注册的自定义动作；
- `method` 只表示 HTTP 请求方法，例如 `GET`、`POST`、`PUT`、`DELETE`；
- 不涉及 HTTP 请求的动作不提供 `method`；
- `action` 不能用 `method` 代替，`method` 也不能表达按钮的交互语义；
- 对标准 CRUD，前端可以根据 `action` 和当前资源上下文推导默认 `method`，只有覆盖默认方法时后端才需要提供 `method`。

API 路径相对于 `/api`，业务配置不重复写 `/api`，也不重复写 `.php` 等后缀。路径前缀和后缀仍由前端通用协议助手处理，这属于基础设施逻辑，不属于业务硬编码。

### 2.3 非标准动作

同步云资源、执行迁移、导出数据等无法从 CRUD 规则推导的操作，使用受限的动作标识：

```ts
{
  key: 'migrate',
  label: '执行迁移',
  action: 'migrate'
}
```

前端只执行预先注册的通用动作，不执行后端下发的 JavaScript。后端 API 仍必须独立完成权限校验，按钮隐藏不能替代接口鉴权。

非标准动作也遵循最小数据原则：如果前端注册的动作可以根据当前页面、当前行和参数生成目标，就不返回路径；只有无法推导时，才允许返回相对于 `/api` 的逻辑路径。

### 2.4 默认 CRUD 权限等级

标准 CRUD 默认采用由低到高的权限等级：

| HTTP 方法 | 默认能力 | 默认等级 | 典型操作 |
|---|---|---:|---|
| `GET` | `read` | 1 | 查看列表、查看详情、刷新 |
| `POST` | `create` / `request` | 2 | 新增记录、提交申请 |
| `PUT` | `update` / `review` | 3 | 修改记录、审核记录 |
| `DELETE` | `delete` | 4 | 删除记录、不可逆操作 |

默认规则下，拥有 `GET` 能力的用户可以读取数据，但不能自动获得 `POST`、`PUT` 或 `DELETE` 能力。后端根据当前用户能力生成动作列表：没有能力的动作不返回，API 本身也必须拒绝对应请求。

HTTP 方法只是标准 CRUD 的默认映射，不是最终权限模型。业务动作可以覆盖默认映射，例如：

```text
POST /sync       -> cloud.sync
POST /apply      -> order.apply
PUT  /review     -> order.review
```

因此权限判断应优先使用业务能力名，例如 `users.read`、`users.create`、`orders.review`、`users.delete`，而不是在所有场景直接比较 HTTP 方法。方法到能力的映射仅作为标准 CRUD 的默认策略。

权限等级不是安全边界的唯一依据。敏感的读取接口仍可以要求高于普通 `GET` 的能力，删除、审核和批量操作也必须在后端逐接口校验。

## 3. 文案与多语言

- [ ] 后端根据请求语言或用户语言配置返回菜单、按钮、字段、确认提示和反馈文案。
- [ ] 前端不维护业务语言包。
- [ ] 数据库和 API 中的稳定值不翻译，例如 `enabled`、`disabled`、`delete`。
- [ ] 显示文本与稳定程序值分离，避免把中文文案作为业务判断条件。
- [ ] 通用 UI 必要的框架文案可以保留在前端，业务文案必须由后端提供。

## 4. 导航与路径

- [x] 站点导航继续由 `server/sites/<site_key>/navigation.mts` 声明。
- [x] 站点继承、角色过滤和导航覆盖继续由后端负责。

- [ ] 明确约定：导航 `key` 是逻辑页面路径，前端统一追加页面后缀；API 资源路径相对于 `/api`，前端统一追加 API 后缀。
- [ ] 为页面路径和 API 路径助手增加测试，覆盖无后缀、`.html`、`.php`、动态 ID 和首尾斜杠。

## 5. 前端职责边界

前端保留以下能力：

- 通用菜单和页面渲染；
- 通用表格、表单、Switch、Select 等控件；
- 受限动作执行器；
- 少量已打包的复杂业务组件注册表，例如阿里云实例详情组件；
- 浏览器路由和页面后缀拼接。

前端不负责：

- 决定业务菜单是否显示；
- 决定业务按钮权限；
- 维护业务页面标题和业务按钮文案；
- 维护具体业务 API URL；
- 通过隐藏按钮实现安全控制。

## 7. 明确不做

- 不把业务导航和权限规则整体搬到前端。
- 不让后端下发可执行代码。
- 不为标准 CRUD 按钮重复返回完整 `href`、`url` 和 `path`。
- 不使用按钮隐藏替代后端 API 权限校验。
- 不为了抽象而建立覆盖所有业务差异的通用 CRUD 框架。
